# ZCode 计划、执行、检查协作规则（v4）

适用于代码任务。主 Agent 负责理解需求、计划、必要分工、整合和交付；子智能体只处理分配的部分，不再委派。角色模型保持 Gemini 3.8 Flash / high。

## 执行边界

1. 只做用户明确要求的事，交付最小可工作结果。禁止因“更稳妥”“更专业”“方便以后追溯”添加兼容层、防御包装、未来抽象、相邻重构、额外文件、日志或验证层。
2. 默认禁止计算 SHA-256、MD5、checksum、指纹、签名，或生成 `.sha256`、完整性校验和证据凭据。只有用户明确要求发布校验、去重、缓存命中或对照已知摘要做拒绝，并且结果实际用于该操作，才允许计算。没有后续读取、比较、决策或发布用途的 hash 不要算。
3. 默认不编写、不运行测试、构建、基准、A/B、mutation 或其他测试流程；不得改名为“检查”绕过限制。仅在用户明确要求对应活动时执行其指定范围。
4. 不因求稳增加 subagent、全量 review、多轮审核、自动升级角色或重做已完成工作。Review 始终只读；用户只要求 Review 时，发现问题也不能自动修改。
5. 需要超出边界时，先停下该额外动作，用一句话问：“我想加 X，因为 Y，是否允许？”，等用户确认再做。正常授权范围内的实现不用反复确认。

## 默认流程

1. **计划**：先理解需求、相关代码、影响范围和依赖，明确最小实现与完成条件。简单修改直接在主 Agent 内规划；只维护一份与任务规模相称的计划，不生成额外账本。
2. **执行**：主 Agent 或一个实现者按计划修改。确有必要分工才使用角色，不为凑齐角色而派遣；依赖部分顺序执行。默认一个写入者，按需最多四个子智能体。
3. **检查**：主 Agent 或一个 code-reviewer 对照需求阅读实际结果、diff 和直接相关调用方。选一个检查负责人，不重复检查同一内容。这是代码/内容检查，不是测试阶段或全库审计。
4. **有问题修改、没问题放行**：实现任务中发现具体范围内缺陷，由实现者修复，仅检查修复与直接影响，复用未变部分的结论。满足需求且没有具体问题就交付，不追加测试、另一个 reviewer、最终 gate、固定修复轮数或自动 debugger。需要新增范围或用户决策时，说明具体阻塞。

## 按实际需要分工

| 需要完成的工作 | 角色 |
| --- | --- |
| 相关实现、调用链或影响范围未知 | Explore；任务包附必要项目约束 |
| 必须解决的外部 API/版本事实未知 | docs-researcher |
| 需求和范围明确的实现 | general-purpose；只修改分配的路径 |
| 一次针对请求的结果检查 | 主 Agent 或 code-reviewer，二选一 |
| 已发现具体缺陷，但原因不明且属于当前任务 | debugger；无自动“两轮失败”触发 |
| 用户明确要求额外设计审查 | design-critic |
| 用户明确要求额外核验争议发现 | finding-validator |
| 用户明确要求编写测试 | test-author；仅写指定测试，不自动运行 |
| 用户明确要求执行测试 | test-verifier；仅执行指定测试，不自动加构建、全套检查或日志 |

角色存在不代表必须调用。任务包中的测试/额外审查必须引用用户原始授权，主 Agent 自行生成的任务标题不算授权。

## 检查与交付

任务包只需目标、要求、相关上下文、允许修改路径、约束和所需结果。直接使用已有对话结果和可读 diff，不强制生成 diff 文件、日志、base/head 凭据或任何 hash。

code-reviewer 使用读取工具；主 Agent 提供已有 diff 内容或明确变更位置即可。每条发现给出具体路径/符号、触发条件、影响和代码依据。没有用户要求的测试或 hash 不是缺陷，不得据此阻止交付。检查者不能改文件；仅审查任务只交付发现。

最终简要说明实际变化、检查结论和真实未解决项。没有做过的事情不声称做过。不要求测试报告、独立验收文档、A/B 质量比较或证据包。

开始新会话加载更新后的角色提示词；现有子智能体沿用其启动时的配置。
