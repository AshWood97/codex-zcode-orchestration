# ZCode 代码质量优先协作规则（v3）

仅适用于软件开发。文档、表格、演示等交付物按各自流程处理。以下编排由主 Agent 执行；子智能体只执行分配的任务包，不能再委派或重复启动流程。所有代码角色使用 Gemini 3.8 Flash，思考深度 high。内置角色模型在设置中指定，七个自定义角色显式指定模型。

## 任务开始与路由

主 Agent 负责需求、架构决策、任务账本、整合与交付。每次任务先记录目标、验收条件、非目标、基线、约束和风险。小范围机械修改直接做并验证；不要为凑齐角色而分派。

| 情况 | 角色及产物 |
| --- | --- |
| 实现位置、调用链、影响面不明 | 内置 Explore：精确路径、调用关系、既有测试与未知项。显式传入项目约束；它默认不读取 AGENTS.md。 |
| 依赖外部 API、版本或上游事实 | docs-researcher：原始出处、版本约束与兼容性结论。 |
| 跨模块契约、架构、数据或恢复语义有重要取舍 | design-critic：实现前的反例、风险、最小调整。 |
| 行为变化、缺陷修复或复杂重构需要新验收 | test-author：从需求和基线独立设计测试、需求—断言表、测试补丁与有效性证据。 |
| 实现范围和验收已明确 | 内置 general-purpose：按 owned_paths 实现，保留冻结测试，报告实际变化与检查。 |
| 行为、公共接口、权限、状态、并发、依赖或整合变化 | test-verifier：独立运行测试/构建/复现，给出准确命令与版本绑定的证据。 |
| 实质代码变化完成 | code-reviewer：实际 diff、上下文、调用方与测试有效性审查。 |
| 实现者或审查者对具体发现有争议 | finding-validator：confirmed / refuted / unresolved，必须以证据裁定。 |
| 同一问题两次修复仍失败，或因果不明 | debugger：先查根因、设计区分实验，再允许下一次修复。 |

## 默认实施顺序

1. 按需探索/查资料，确定需求和边界；重要设计再做独立批评。主 Agent 修订同一份计划，不反复开新的规划流程。
2. 对实质行为变化，让 test-author 先读需求、基线和已有测试习惯，不提供实现者思路或自评。测试与实现可在分开的副本并行；共享契约必须先定清楚。
3. 主 Agent 检查测试质量并冻结验收测试版本/hash。默认一个实现写入者；明确互不重叠且可独立整合时才并行。总并发不超过四个子智能体；共享接口、数据库、状态或调用链依赖按顺序处理。内置 general-purpose 的任务包必须重申禁止修改冻结测试。
4. 整合完成后，在独立临时 Git 副本执行 test-verifier；检查 tracked diff 前后不变，缓存不回流。只读权限是提示和工具约束，不能把工具白名单当作文件系统沙箱。无法隔离时串行执行并明确记录限制。
5. 保存可读取的实际 diff、base/head、变更文件、需求和测试证据给 code-reviewer。它只有读取工具，不能假设能自行执行 git diff。审查与测试无依赖时可并行，交付必须汇总两者。
6. 有争议的发现交 finding-validator；unresolved 的重要风险仍阻止完成，不以多数票否定单个有效发现。确有证据的缺陷由实现者修复；测试错误由 test-author 根据需求修订，再独立复核并重跑。
7. 修复后使用新 reviewer 实例，仅聚焦原发现、新 diff 与相关调用方；重跑受影响测试。相同问题失败两轮后进入 debugger；整个任务最多五轮自动修复。到达上限报告具体未解决项，不把停止当作完成。

## 验收与证据

- 测试必须映射到需求。缺陷修复要求旧版以正确行为原因失败、新版通过；环境/安装/导入失败不算复现。新功能覆盖边界与错误；重构验证行为保持，不强迫旧版失败。
- mock 不得替代核心被测逻辑。按风险采用性质测试、差分或局部 mutation；不要机械增加无效测试或追求数字。
- 实现者可提出测试异议，须提供需求冲突与反例。禁止静默削弱断言、跳过测试或修改快照迎合实现；测试变更记录原因、版本和独立复核证据。
- 根据实际变化给 reviewer/verifier 加相应审查维度：跨模块整合；认证/权限安全；并发、重试、事务；性能基准；UI 真实端到端流程；抽象与重复的维护成本。无需增加一堆常驻角色。
- 代码、测试、需求、依赖或环境版本变化会使相关测试/审查结论过期，必须重跑；没有执行、环境失败、证据过期均不能算通过。
- 子任务包给出 task_id、目标、验收、base/head、约束、依赖、owned_paths（写任务）、禁止事项、可读 diff/日志路径与结果格式；不转发整段聊天。
- 主 Agent 维护任务账本：角色、基线、代码/测试版本、状态、发现三态、执行命令、exit code、日志/hash、修复次数、未知项。测试设计、测试执行和代码审查证据分开记录。
- 最终交付必须满足需求、通过相关检查、解决重要缺陷、检查最终 diff；有真实用户风险则直接说明。不要把外部排行榜或模拟测试当作本机实测。

## 可选的双候选实验

仅对确有重要不确定性的设计/实现，在同一基线的两个隔离副本探索。候选使用相同需求、测试与预算；用有区分力的测试和独立审查选择一个，并记录理由。只整合获选候选，禁止把两个互斥补丁都合入。尚未通过本地盲测证明收益，不默认启用。

配置更新后开始新会话，旧子智能体不会自动重载角色设置。
